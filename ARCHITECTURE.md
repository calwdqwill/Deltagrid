# Архитектура DeltaGrid

## Текущее состояние

DeltaGrid — аналитическое приложение для крипторынка с FastAPI backend, Next.js frontend и PostgreSQL persistence layer. Текущий MVP содержит market dashboard, scanner, data-layer endpoint'ы, auth, paper trading, execution foundation, alerts, RWA/treasury и backtesting foundation.

## Основные слои

- `frontend/` — Next.js 15, React, TypeScript, Tailwind CSS, Zustand, TanStack Query и `lightweight-charts` для interactive charts.
- `backend/app/api/v1/` — FastAPI routes и API boundary.
- `backend/app/services/` — бизнес-логика: market, scanner, alerts, execution, RWA, treasury, auth.
- `backend/app/adapters/` — внешние провайдеры и exchange/data adapters.
- `backend/app/adapters/data/sync_market_data.py` — production-safe команда для первичного и повторного наполнения data-layer из OKX USDT swaps, CoinGlass v4 и CoinGecko-derived spot snapshots. Binance adapter сохранён как legacy/diagnostic path, но на текущем production VPS direct Binance API возвращает HTTP `451`.
- `backend/app/adapters/data/okx_adapter.py` — primary CEX perp adapter для MVP1: OHLCV candles, funding history, open interest snapshots и long/short account ratio.
- `backend/app/services/providers/hyperliquid_client.py` — read-only direct Hyperliquid public client для live Perp DEX snapshot v0 через `POST /info` с `type=metaAndAssetCtxs`; не пишет в БД и не включает execution.
- `backend/app/services/providers/dydx_client.py` — read-only dYdX v4 Indexer client для live Perp DEX snapshot v0 через `GET /perpetualMarkets`; не пишет в БД и не включает execution.
- `backend/app/services/providers/lighter_client.py` — read-only Lighter public client для live Perp DEX snapshot v0 через `GET /orderBooks`, `GET /orderBookDetails` и `GET /funding-rates`; не пишет в БД и не включает execution.
- `backend/app/services/providers/aster_client.py` — read-only Aster public Futures client для live Perp DEX snapshot v0 через `GET /fapi/v1/exchangeInfo`, `GET /fapi/v1/premiumIndex`, `GET /fapi/v1/ticker/24hr`, `GET /fapi/v1/openInterest`, `GET /fapi/v1/ticker/bookTicker` и display-only `GET /fapi/v3/depth`; не пишет в БД и не включает execution.
- `backend/app/services/providers/gmx_client.py` — read-only GMX public client для Perp DEX raw snapshot v0 через `GET /markets/info`; сохраняет GMX fixed-point/token-unit поля как raw strings, масштабирует `poolAmountLong/Short` в token units через decimals из `/tokens`, не пишет в БД и не включает execution.
- `backend/app/services/providers/coinglass_client.py` — CoinGlass v4 client для CEX enrichment streams и read-only Perp DEX enrichment v0 через futures `coins-markets`; Perp DEX rows являются third-party aggregate diagnostics, не пишутся в БД и не включают route ranking/execution.
- `backend/app/domain/models.py` — SQLAlchemy ORM-модели.
- `backend/app/persistence/` — sync/async DB engines и Alembic migrations.

## База данных

Основная БД для MVP — PostgreSQL. Подключение задаётся через `DATABASE_URL`.

- Sync API routes используют SQLAlchemy engine с `psycopg`.
- Async persistence helper использует `asyncpg`.
- Alembic использует sync URL и выполняет `upgrade head`.
- `Base.metadata.create_all()` оставлен только для SQLite fallback в isolated tests.
- Docker Compose поднимает PostgreSQL 16 и запускает миграции перед стартом backend.
- `GET /api/v1/health/readiness` проверяет локальное подключение к БД и совпадение текущей Alembic revision с source head.

SQLite больше не является production runtime. Он может использоваться только явно в тестах, например `sqlite:///:memory:`.

При `DEBUG=false` startup validation блокирует слабые/dev secrets, пустой `VAULT_MASTER_KEY`, SQLite `DATABASE_URL` и wildcard `CORS_ORIGINS`.

## Deployment Boundary

Локальный `docker-compose.yml` остаётся dev/staging-friendly и публикует PostgreSQL на `5432` для удобной проверки. Для сервера добавлен отдельный `docker-compose.prod.yml`: PostgreSQL не публикуется наружу, backend и frontend слушают только `127.0.0.1`, а внешний доступ должен идти через reverse proxy.

Frontend HTTP API использует относительный `/api/v1` и проксируется Next.js rewrite'ом на `BACKEND_INTERNAL_URL`. Так как Next.js запекает rewrites во время build, Docker Compose передаёт `BACKEND_INTERNAL_URL=http://backend:8000` через frontend build args. WebSocket stream выбирает `NEXT_PUBLIC_WS_URL`, если он задан, иначе использует `127.0.0.1:8000` локально и same-origin `/api/v1/stream/ws` на production-домене.

Для server-rendered frontend screens добавлен лёгкий helper `frontend/src/lib/server-api.ts`: он читает `BACKEND_INTERNAL_URL` или `NEXT_PUBLIC_API_URL` и обращается к backend без клиентского auth/Zustand слоя. Сейчас основные terminal screens читают live backend/data-layer вместо `terminalDataAdapter`: `Market Overview` использует `GET /api/v1/market/markets`, `/market/global`, `/market/fear-greed`, `/market/funding-rates` и `/data/health`, `Assets` использует `/market/markets`, `/market/funding-rates`, `/data/ohlcv`, `/data/liquidations` и `/data/health`, `Charts`, `Market Matrix` и `Arbitrage Scanner` используют persisted OHLCV/funding/OI/long-short/basis streams.

`/charts` теперь имеет отдельный client-side слой `InteractiveCandlestickChart` на `lightweight-charts`. Server-side workspace собирает OKX OHLCV окно через `/data/ohlcv/window`, а старая постраничная сборка поверх `/data/ohlcv` оставлена fallback path. Client layer отвечает только за визуализацию candles, volume, crosshair и pan/zoom/scroll; расчёты data quality, freshness и coverage остаются в backend/data-layer.

Data-layer API открыт read-only endpoint'ами: `/data/ohlcv`, `/data/ohlcv/window`, `/data/funding`, `/data/open-interest`, `/data/long-short-ratio`, `/data/basis-premium`, `/data/liquidations`, `/data/coverage`, `/data/universe`, `/data/provider-inventory` и `/data/health`.

Для interactive charts добавлен отдельный read-only endpoint `/data/ohlcv/window`. Он возвращает bounded OHLCV окно по `symbol + exchange + interval + range`, ограничивает размер ответа `20000` строками и, если `end` не задан, использует последнюю доступную свечу в PostgreSQL как правый край окна. Старый `/data/ohlcv` сохраняет лимит `1000` строк для общих read-side сценариев.

`/data/health` остаётся read-only health snapshot без внешних API-вызовов. Помимо provider-level статусов и row counts он возвращает:

- `freshness` — SLA по `symbol + exchange + stream + interval` для `BTC/ETH/SOL` на primary exchange `okx`, включая `latest_timestamp`, `age_minutes`, expected cadence и статус `fresh/stale/degraded`;
- `coverage` — инвентаризацию исторического покрытия по `symbol + exchange + stream + interval`: фактические строки, expected rows, coverage %, latest timestamp и reason для OHLCV/funding/OI/long-short/liquidations/basis/spot-perp price;
- `universe` — policy view для текущего MVP universe: `complete_history`, `core_perp_ready`, `partial_history`, `not_ready`, `policy.ui_universe` и `deferred_symbols`;
- `sync_health_by_type` — последние sync-runs по `provider_name + sync_type`, чтобы OHLCV, funding, OI, long/short, liquidations и basis были видны отдельно;
- `sync_diagnostics` — cron-path диагностику по `provider_sync_runs`: последний запуск, последний успешный запуск, fetched/inserted records и классы ошибок вроде `http_451`, `rate_limit`, `circuit_breaker`, `empty_response`.

`/data/provider-inventory` — отдельный read-only endpoint для MVP1 expansion gate. Он строит inventory candidate symbols поверх persisted coverage/freshness, возвращает `promotion_candidate`, `chart_ready_candidates`, `policy.gates`, `next_action`, readiness status и summaries по 24h/7d. Для объяснения strict gate endpoint также возвращает `coverage_blockers_7d`, `freshness_blockers`, объединённый `promotion_blockers`, summary-разбивку blocker'ов по stream и summary-разбивку по `resolution_strategy`, чтобы было видно, какие persisted signals блокируют full analytics promotion и как их закрывать. Каждый blocker содержит `resolution_strategy`, `historical_backfill_supported`, `minimum_collection_window_hours`, `resolution_action` и `resolution_reason`. В текущем ingestion path `ohlcv`, `funding_rates` и `long_short_ratio` считаются `history_backfill_supported`, `liquidations` — `provider_sync_required`, а `open_interest`, `basis_premium` и `spot_perp_price` — `snapshot_accumulation_required`, потому эти потоки пишутся как snapshots и не могут быть честно восстановлены одним запуском `--lookback-hours 168`. `chart_ready` и `chart_ready_candidates` означают только готовность для preview `/charts` и `/assets`; `promotion_candidate` для full analytics universe требует `complete_history` и не выдаётся для `core_perp_ready`, если snapshot/enrichment streams ещё partial. В отличие от `/data/health`, который остаётся scoped к текущему UI universe `BTC/ETH/SOL`, provider inventory считает freshness по запрошенным candidate symbols и возвращает `scope.freshness_scope=requested_symbols`. Endpoint не вызывает внешние API и не меняет sync-конфигурацию; внешний discovery OKX/CoinGlass/CoinGecko/legacy Binance остаётся отдельным CLI-шагом перед расширением `SymbolMapper` и UI universe.

Для внешнего discovery добавлен CLI `python -m app.adapters.data.discover_provider_universe`. Он не является API endpoint'ом и не пишет в PostgreSQL: задача CLI — проверить live provider availability для candidate symbols перед изменением aliases/sync universe. Проверяются OKX USDT swap instrument/OHLCV/funding/OI/long-short, CoinGlass OKX snapshots/liquidations, CoinGecko spot price и Binance USD-M как legacy diagnostic. На VPS Binance остаётся `blocked_http_451`, поэтому не используется как primary path.

`SymbolMapper.seed_defaults()` теперь идемпотентно поддерживает core symbols `BTC/ETH/SOL` и первую малую expansion group `HYPE/XRP/DOGE/ADA/LINK`. Эти aliases нужны для preview sync dry-run и CoinGecko-derived basis, но сами по себе не расширяют UI universe: `/data/provider-inventory` и freshness SLA остаются gate перед показом новых symbols в product screens.

Для sparse event streams, сейчас это `liquidations`, freshness разделяет два сигнала: возраст последнего события и возраст последнего успешного sync-run. Если новых liquidation events нет, но `coinglass/liquidations` sync свежий и успешный, поток остаётся `fresh` с reason `no recent liquidation events`; `/data-health` показывает это как `event age / sync age`.

`Perp DEX` больше не ограничен только pending-state: для Hyperliquid подключён read-only live snapshot endpoint `GET /api/v1/perp-dex/venues/hyperliquid/markets`, который возвращает mark/mid/oracle price, funding, open interest, 24h volume, premium, impact prices и leverage metadata из public provider API. Для dYdX подключён `GET /api/v1/perp-dex/venues/dydx/markets`, который читает v4 Indexer `perpetualMarkets` и возвращает oracle price как mark proxy, 24h price change, funding, open interest, 24h volume, trades, margin fractions, tick/step size и leverage estimate. Для Lighter подключён `GET /api/v1/perp-dex/venues/lighter/markets`, который читает public `orderBooks`, `orderBookDetails` и `funding-rates`, возвращает last trade price как display price, funding, OI USD estimate, 24h volume, trades, maker/taker fee, margin fractions, tick/step size и `normalization_status=lighter_public_market_details`; это direct read-only market context, а не route scoring input. Для Aster подключён `GET /api/v1/perp-dex/venues/aster/markets`, который читает public Futures `exchangeInfo`, `premiumIndex`, `ticker/24hr`, `openInterest` и `ticker/bookTicker`, возвращает mark/index/mid price, funding, OI USD estimate, 24h volume, trades, top-of-book, tick/step size, min notional и `normalization_status=aster_public_futures_market_data`; fee tiers, depth/slippage и carry conversion не считаются production signal. Для GMX подключён `GET /api/v1/perp-dex/venues/gmx/markets`, который читает Arbitrum `markets/info` и возвращает market rows как `partial`/`raw_fixed_point`: `fundingRate*`, `borrowingRate*` и `netRate*` сохраняются как raw strings без пересчёта в percent/cost, `poolAmountLong/Short` масштабируются в token units через decimals из `/tokens`, а `openInterestLong/Short` и `availableLiquidityLong/Short` масштабируются через `1e30` в diagnostic-only USD strings. Тот же GMX client читает `/tokens` и резолвит `index/long/short` token symbols/decimals; это только diagnostics (`scale_validation_status=token_decimals_resolved`, `token_amount_scale_status=pool_amounts_scaled`, `diagnostic_usd_scale_status=usd_diagnostics_scaled`, `rate_semantics_status`, `rate_relation_summary` и `rate_source_fields_summary` для relation guardrail), а не разрешение использовать raw fixed-point metrics как normalized USD/OI/liquidity/carry. Production поля `open_interest_usd` и liquidity ranking для GMX остаются пустыми/заблокированными. Это live request path, а не persisted historical data-layer: snapshots пока не сохраняются в PostgreSQL. `GET /api/v1/perp-dex/route-constraints` возвращает static read-only policy без внешних API-вызовов: `research_only`, normalized vs raw venues, blockers для GMX fixed-point formula validation, fees/slippage model и execution boundary. `GET /api/v1/perp-dex/route-model` возвращает static read-only route model v0: checklist обязательных входов, venue readiness и formula skeleton для fees/slippage/routing без numeric estimates, ranking и execution. В policy есть `lighter_direct_snapshot` и `aster_direct_snapshot`: source-backed notes фиксируют safe use для public endpoints и блокируют route-level liquidity ranking, slippage/depth curve, carry-cost conversion и execution selection. Cost semantics metadata v0 дополнительно фиксирует, что Lighter `maker_fee`/`taker_fee` и Aster top-of-book являются display fields, но не route-ready fee/depth/slippage inputs без account tier, order intent, depth curve, carry horizon и execution boundary. В policy есть `gmx_formula_validation`: source-backed notes подтверждают diagnostic-only `poolAmountLong/Short`, `Precision=1e30` для factors, разделение contract paths `openInterest`/`openInterestInTokens` и diagnostic-only USD decimals для GMX ticker OI/liquidity. В route model также есть `gmx_rate_semantics`: source-backed metadata говорит, что GMX interface `MarketTicker` считает `fundingRate*` и `borrowingRate*` за 1h, а offline guardrails проверяют ожидаемую relation `netRate* = fundingRate* - borrowingRate*` и observed live-shape fixture; live smoke вернул `raw_rate_relation_plus_with_zero_borrowing`, где nonzero-borrowing sides совпали с `funding+borrowing`, а zero-borrowing sides помечены ambiguous. Current `/markets/info` payload также не отдаёт helper inputs `fundingFactorPerSecond`, `borrowingFactorPerSecondForLongs/Shorts` и `longsPayShorts`, поэтому live mapping, funding sign и borrowing carry требуют отдельного разбора, side-aware fixtures, holding period и position notional. Fees/slippage/routing остаётся только модельным каркасом до sourced fee/depth/carry inputs, поэтому multi-DEX volume/OI/liquidity не считается полным production signal. `Strategy Lab` показывает readiness live inputs, но не показывает fake PnL/trades до появления реального backtest engine.

`diagnostic_cost_estimate_v0` внутри `GET /api/v1/perp-dex/route-model` является только компонентным diagnostic layer. Он может показывать Aster `top_of_book_spread_bps`, top-level depth summaries и published Aster USDT-perp fee defaults как metadata, но не суммирует components в total cost bps, не ранжирует venues и не открывает execution path. Lighter fee fields остаются raw public fields до подтверждения units, account fee tier, maker/taker side и order intent.

`Route Diagnostic Components Summary` в frontend `Perp DEX` является presentation summary поверх `diagnostic_cost_estimate_v0.components`: он показывает количество diagnostic components, display-only outputs, blocked numeric components, sourced component fields и статус numeric total bps. `scripts/perp-dex-policy-smoke.sh` и backend regression tests проверяют обязательные component ids, `status`, `source_fields`, `blocked_by` и `safe_use`, чтобы component diagnostics оставались machine-readable и не превращались в total route-cost estimate.

`diagnostic_cost_estimate_v0.summary` является backend machine-readable контрактом для этого summary-layer. Он агрегирует `component_count`, `display_only_component_count`, `blocked_numeric_component_count`, `sourced_component_count`, component id списки и `numeric_total_status=blocked` поверх того же списка `components`. Frontend использует backend summary как основной источник для `Route Diagnostic Components Summary` и оставляет fallback на локальный расчёт из `components`; smoke и regression tests проверяют, что summary не расходится с component list.

`summary.venue_breakdown` группирует те же diagnostic components по venue (`lighter`, `aster`, `all`) и отдаёт counts/id-списки для display-only, blocked numeric и sourced components. Frontend `Route Diagnostic Venue Breakdown` показывает этот слой рядом с общей summary; при отсутствии backend breakdown UI может восстановить его из `components`. Это помогает видеть venue-level readiness, но не даёт route cost, venue ranking или execution signal.

`summary.blocker_breakdown` группирует `components[*].blocked_by` по повторяющимся blocker reasons и отдаёт component ids, venue ids, display component ids и blocked numeric component ids. Frontend `Route Diagnostic Blocker Breakdown` показывает этот слой перед детальной component table; при отсутствии backend breakdown UI может восстановить его из `components`. Это помогает видеть, какие inputs блокируют numeric route cost чаще всего, но не разрешает route scoring.

`summary.required_input_breakdown` группирует `components[*].required_input_ids` по обязательным входам route model (`venue_fee_schedule`, `order_intent`, `depth_or_impact_model`, `carry_horizon`, `risk_limits`) и отдаёт component ids, venue ids, display component ids, blocked numeric component ids и sourced component ids. Frontend `Route Diagnostic Required Input Breakdown` показывает этот слой после blocker breakdown; при отсутствии backend breakdown UI может восстановить его из `required_inputs` и `components`. Это помогает видеть coverage обязательных inputs, но не разрешает route scoring.

`summary.source_field_breakdown` группирует `components[*].source_fields` по sourced display fields и отдаёт component ids, venue ids, required input ids, display component ids и blocked numeric component ids. Frontend `Route Diagnostic Source Fields Breakdown` показывает, какие поля уже доступны как display context, но не считает их route-cost inputs.

`summary.source_input_action_coverage` связывает `summary.source_field_breakdown` с `summary.next_action_breakdown`: для каждого sourced display field видны component ids, venue ids, required input ids, mapped next action ids/actions и source types. Frontend `Route Diagnostic Source Input Actions` показывает, какие display fields уже есть, но какие actions всё ещё нужны до route-ready use. `numeric_total_status=blocked` сохраняет границу: это coverage/readiness mapping, а не route-cost input, ranking signal или execution permission.

`summary.route_ready_evidence_checklist` группирует pre-route-scoring gates по fee schedule, order intent, depth freshness, depth aggregation, carry semantics и risk limits. Каждый gate показывает required route inputs, required policy inputs, component ids, policy ids, sourced evidence fields, blocked outputs и явные флаги `may_estimate_cost_bps=false`, `may_rank_routes=false`, `may_submit_orders=false`. Frontend `Route Diagnostic Evidence Checklist` показывает этот слой после source/input/action coverage; это checklist готовности evidence, а не разрешение считать route cost, сортировать venues или отправлять orders.

`summary.fee_schedule_evidence_summary` и `summary.fee_schedule_evidence_checklist` добавляют отдельный read-only слой по Lighter/Aster fee schedule evidence. Rows `lighter_fee_schedule_evidence` и `aster_fee_schedule_evidence` показывают public/source fee fields, required inputs, required policy inputs, account tier/order intent/manual approval gates, blocked outputs и явные флаги `may_emit_fee_bps=false`, `may_estimate_cost_bps=false`, `may_rank_routes=false`, `may_submit_orders=false`. Frontend `Route Diagnostic Fee Schedule Evidence` и `Route Diagnostic Fee Schedule Checklist` показывают эти gates рядом с readiness/depth policy слоями; это не fee bps total, не numeric route cost и не route ranking.

`summary.venue_evidence_status` раскладывает эти gates по Lighter, Aster, GMX и cross-venue scope. Для Lighter/Aster row показывает direct venue components, policy ids, source fields, venue gates и cross-venue gates. Для GMX row показывает `gmx_rate_mapping_review`, diagnostic fields (`rate_relation_summary`, `rate_source_fields_summary`) и fixture coverage ids. Все rows сохраняют `may_estimate_cost_bps=false`, `may_rank_routes=false`, `may_submit_orders=false`: это разделение evidence gaps, а не venue ranking.

`summary.safe_use_breakdown` группирует `components[*].safe_use` по boundary text и отдаёт component ids, venue ids, required input ids, display component ids и blocked numeric component ids. Frontend `Route Diagnostic Safe Use Breakdown` помогает видеть, где UI должен оставаться в diagnostic/display режиме и не превращаться в route signal.

`summary.readiness_rollup` агрегирует component readiness в compact категории `fees`, `depth_slippage`, `carry` и `risk_limits`. Rollup показывает required input ids, component counts, sourced counts, display ids, blocked numeric ids и next action, но сохраняет `numeric_total_status=blocked` и не даёт route cost, venue ranking или execution signal.

`summary.depth_staleness_policy_checklist` фиксирует depth freshness/stale-depth gates для Lighter `orderBookOrders`, Aster `ticker/bookTicker` и Aster `fapi/v3/depth`. Каждый policy row связывает venue, component, source endpoint, source fields, required policy inputs (`depth_snapshot_timestamp`, `max_depth_age_ms`, `stale_depth_action`, `order_size_usd`, `side`, `depth_aggregation_policy`, `liquidity_cap`) и blockers. `may_emit_slippage_bps=false` и `numeric_total_status=blocked` остаются обязательными инвариантами: checklist нужен для observability и следующего research шага, а не для расчёта slippage bps, route cost или ranking.

`summary.required_policy_input_breakdown` группирует required policy inputs из `summary.depth_staleness_policy_checklist`. Каждый row показывает, какие policy ids, component ids, venue ids, source endpoints и blockers зависят от конкретного input (`depth_snapshot_timestamp`, `max_depth_age_ms`, `stale_depth_action`, `order_size_usd`, `side`, `depth_aggregation_policy`, `liquidity_cap`). `may_emit_slippage_bps=false` и `numeric_total_status=blocked` сохраняют границу: это readiness matrix для policy inputs, а не slippage model.

`summary.next_action_breakdown` группирует planning actions из `summary.required_input_breakdown`, `summary.readiness_rollup` и `summary.depth_staleness_policy_checklist`. Каждый row показывает `source_types`, `source_ids`, required route inputs, required policy inputs, component ids, venue ids, policy ids и rollup categories, но сохраняет `numeric_total_status=blocked`. Это слой планирования research gaps, а не разрешение считать route cost, сортировать venues или выбирать route.

`gmx_rate_mapping_review_v0` — отдельный read-only блок в `GET /api/v1/perp-dex/route-model`. Он агрегирует уже существующие GMX rate diagnostics (`rate_relation_summary`, `rate_relation_diagnostics`, `rate_source_fields_status`, `rate_source_fields_summary`) в review items: source relation guardrail, live nonzero-borrowing mapping, source helper inputs и carry conversion boundary. ## Типы данных

- Даты в ORM сейчас хранятся как UTC-naive `DateTime`.
- Market time-series и backtest time windows используют Unix timestamp в миллисекундах в `BigInteger`-полях.
- JSON-like поля сохраняются как `Text` с суффиксом `_json`, чтобы не менять существующую сериализацию.
- Финансовые значения PnL, balances, RWA/treasury используют `DECIMAL`.
- OHLCV/funding/OI market data пока используют `Float`; это допустимо для MVP-аналитики, но требует пересмотра перед точными расчётами PnL/execution.
- CoinGlass funding snapshots сохраняются в `funding_rates.funding_rate` как decimal; v4 percent-like значения делятся на `100`. При OKX primary snapshot-запросы идут с `exchange_list=OKX`.
- CoinGlass aggregated liquidation history сохраняется в `liquidations.value_usd` как long/short USD-снимки с exchange primary provider (`okx` для MVP1); `quantity` и `price` равны `0.0`, потому что этот источник не является per-order tape.
- `basis_premium` — approximate snapshot: CoinGecko spot price сравнивается с последним 1m close primary perp provider. Для MVP1 primary provider — OKX USDT Swap. Это аналитический MVP-снимок, не execution-grade pricing.

## Риски и tech debt

- Исторические JSON-поля пока не переведены на PostgreSQL `JSONB`.
- Часть data-layer чисел использует `Float`; для финансово-критичных расчётов нужны `DECIMAL` и отдельная проверка формул.
- Перед следующими production-итерациями нужно добавлять backup PostgreSQL перед миграциями и проверять `certbot renew --dry-run`.
- Старые SQLite `.db` файлы не мигрируются автоматически; если нужны исторические данные, потребуется отдельный экспорт/импорт.
- Нужно регулярно проверять `GET /api/v1/health/readiness` в staging/prod, чтобы ловить рассинхрон Alembic до открытия пользовательского трафика.
- Market data ingestion для production MVP запускается через `scripts/sync-market-data.sh`; на сервере используется host-level cron `/etc/cron.d/deltagrid-market-sync`. По умолчанию sync использует `--primary-perp-provider okx`.
- Основной frontend terminal больше не использует `terminalDataAdapter` в app routes. Оставшийся долг — не mock UI, а отсутствующие production-grade источники для DEX venues, order book, per-order liquidations tape и backtest engine.
